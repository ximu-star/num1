## 1. 项目目标

实现一个面向企业合同审批场景的自动审查系统：
1. 定时自动拉取飞书待审合同，下载附件并解析（预处理）
2. 法务在飞书评论区@合同审批助手时，触发规则审查并输出结果
3. 如果预处理还没完成，先记下来，预处理完了自动开始审查
4. 审查结果回写到飞书审批评论区

**支持格式**：PDF（原生+扫描）、Word（.docx）、图片（jpg/png）。

**交付物**：可运行工具服务 + 数据库初始化脚本 + 示例合同 + 工具调用说明 + 完整闭环演示。

## 2. 整体架构

### 2.1 服务拓扑

```
飞书审批系统（外部）
    |
    | 拉待办 / 监听@消息 / 回写评论（飞书开放平台 API）
    v
ContractReviewService (8001，原Ecommerce改造)
    |
    +-- 拉取模块：APScheduler 每分钟拉待办，下附件，解析
    +-- 附件模块：Word转PDF，多附件拼接，存MinIO
    +-- 解析模块：调MinerU解析PDF -> Markdown（从掌柜智库拷）
    +-- 规则模块：PG确定性规则 + Milvus语义检索，两路命中
    +-- 回写模块：生成评论，调飞书API写评论区
    +-- 日志模块：全链路日志
    |
    +--> PostgreSQL（8张表，含确定性规则表）
    +--> Milvus（手册切片向量库，语义检索参考）
    +--> MinIO（合同附件存储）
    |
    v
AIService (8002)                  Harness 校验层 + Skill 领域路由
    |
    +-- 4个Skill：合同拉取 / 合同解析 / 规则审查 / 报告回写
    |
    +-- 三层校验：结构校验 / 事实校验 / 动作校验
    +-- 重试机制：校验失败 → 反馈给AI → 重新生成（最多1次）
    +-- 异常分级：哪一步失败了，决定blocked还是重试
    +-- Skill调用记录：全链路工具调用日志
    |
    v
掌柜智库（仅离线导入，不作为运行时依赖）
    |
    +-- 导入阶段：造价规范手册PDF -> MinerU解析 -> 切片（从掌柜智库拷逻辑）
    |   -> 人工提炼硬规则存PostgreSQL（20-30条核心规则）
    |   -> 全部切片向量化存Milvus（71页手册原文）
    +-- 定时同步：手册更新后自动同步到Milvus，标记版本，区分增量/全量
```

### 2.2 各服务职责

| 服务 | 端口 | 改造动作 |
|---|---|---|
| ContractReviewService（原Ecommerce） | 8001 | 核心业务服务：拉取/附件/解析/规则/回写/日志六大模块，8张表 |
| AIService | 8002 | Harness 三层校验器 + 4个Skill领域路由 + 重试机制 + 异常分级 |
| 掌柜智库（离线） | 8003（可选） | 导入手册到PG规则表 + Milvus向量库，定时同步；只作为离线导入工具，不参与在线审查 |
| Web前端 | 5173/5174 | 管理后台：任务监控 + 失败重试 + 规则配置 |

### 2.3 两阶段触发模式

| 阶段 | 触发方式 | 做什么 |
|---|---|---|
| **预处理阶段** | APScheduler 定时（每分钟） | 拉待办 → 下附件 → Word转PDF → MinerU解析 → 存合同解析结果 |
| **审查阶段** | 飞书评论区@合同审批助手 | 触发规则审查 → 生成报告 → 回写评论区 |

**预处理完自动审查**：如果预处理还没完成就收到@，先记下来，等预处理完了自动跑审查，不用法务再@第二次。

### 2.4 服务调用约定

- 8001 是唯一有业务库写权限的服务；8002 不直连业务库。
- 业务型 Tool（拉待办、下附件、解析、跑规则、检索、存结果、回写）实现在 8001，8002 通过内部接口调用并包装成 Tool。
- 8002 只负责 LLM 调用和 Harness 校验。
- 8003 只做离线导入，不在在线链路上。

## 3. 核心流程

### 3.1 预处理流程（定时自动跑）

```
APScheduler 每分钟触发
    |
    v
调飞书API拉待办
    |
    v
按approval_code去重
    |
    +-- 已存在的审批单 → 检查附件有没有更新（file_token / sha256）
    |   -> 附件更新了 → attachment_version+1，重新下载、重新解析、重新预处理；旧解析结果保留并标记 superseded
    |   -> 附件没更新 → 跳过
    |
    +-- 新审批单 → 入队（pending）
    |
    v
下载所有附件
    |
    +-- Word附件 → LibreOffice 转 PDF
    +-- 多个附件 → 全部转成PDF后拼接成一个PDF
    |
    v
存 MinIO
    |
    v
调 MinerU 解析 PDF → Markdown
    -> 标记是不是扫描件 OCR（is_scanned）
    |
    v
AI 提取结构化条款（按掌柜智库切片方式：按标题切section → 长切短合）
    |
    v
任务状态 → ready（预处理完成）
    |
    v
检查：这个任务有没有被@过？（review_requested = true？）
    |
    +-- 是 → 自动触发规则审查
    |
    +-- 否 → 等着，下次@再跑
```

### 3.2 审查流程（@触发 或 预处理完自动触发）

```
收到@消息（根据审批编号匹配 approval_tasks）
    |
    v
查任务状态
    |
    +-- done（已审过）→ 直接回复已有的审查结果，不重新跑
    |
    +-- ready → 正常跑审查
    |
    +-- pending/parsing → 设 review_requested = true，不跑，等预处理完自动跑
    |
    +-- blocked → 回复"合同预处理失败，请联系管理员"
    |
    v
加载 Skill 3：规则审查（两路）
    -> 第一路：PG规则表跑确定性规则（阈值/关键词/正则）
    -> 第二路：Milvus向量检索手册参考（is_semantic 规则）
    -> 检查是不是标准版本合同：
       -> 标准版 → 只审可修改部分条款
       -> 非标准版 → 全量审查
    -> 两路结果合并写rule_hits
    -> AI生成风险摘要（走事实校验）
    |
    v
加载 Skill 4：报告与回写
    -> save_result（存审查报告，走结构校验）
    -> write_comment（回写飞书评论区，走动作校验）
    |
    v
任务状态 → done
```

### 3.3 任务状态流转

| 当前状态 | 触发 | 下一状态 | 说明 |
|---|---|---|---|
| pending | 调度器抢占 | parsing | 条件更新 `WHERE task_status='pending'` |
| parsing | 解析成功 | ready | 写 contract_parses |
| parsing | 任一步失败 | blocked | failed_stage=preprocess |
| ready | @ 或 review_requested | reviewing | 条件更新抢占 |
| reviewing | 审查+回写成功 | done | 写 review_results / comment_logs |
| reviewing | 失败 | blocked | failed_stage=review/writeback |
| blocked | 管理员重试 | parsing / reviewing | 按 failed_stage 回到对应步骤 |
| done | 附件更新 | parsing | attachment_version+1，按新版本重审 |
| done | 再次 @ | done | 只回已有结果，不重复回写 |

同一任务的抢占统一用条件 UPDATE，避免定时任务、飞书事件、人工重试并发重复执行。

## 4. Skill 领域设计（4个）

### 4.1 Skill 1：合同拉取（APPROVAL_FETCH）

- **描述**：拉取飞书待审审批单、查详情、下载合同附件、Word转PDF
- **包含的 Tool**：
  - list_pending_approvals：拉待办列表
  - get_approval_detail：查审批详情
  - download_attachment：下载所有合同附件
  - convert_word_to_pdf：Word 转 PDF（LibreOffice）
  - merge_pdfs：多个 PDF 拼接成一个
- **使用指引**：
  1. 先调 list_pending_approvals 拉待办列表
  2. 对每个新审批单调 get_approval_detail 查详情
  3. 调 download_attachment 下载所有附件
  4. Word 附件先调 convert_word_to_pdf 转成 PDF
  5. 所有 PDF 用 merge_pdfs 拼接成一个完整合同 PDF
  6. 存 MinIO
  7. 下载/转换失败，任务进 blocked

### 4.2 Skill 2：合同解析（CONTRACT_PARSE）

- **描述**：解析合同 PDF，切片，提取结构化条款
- **包含的 Tool**：
  - parse_contract：调 MinerU 解析 PDF 为 Markdown
  - split_markdown：按标题切片（掌柜智库方式）
  - extract_clauses：AI 提取结构化条款
- **使用指引**：
  1. 先调 parse_contract 解析 PDF 为 Markdown
  2. 标记 is_scanned：是不是扫描件 OCR
  3. 调 split_markdown 按标题切 section → 长切短合（chunk_size=300, overlap=30）
  4. 调 extract_clauses 从切片里提取结构化条款
  5. 提取结果必须保留原文片段和页码位置
  6. 解析失败要记录原因，任务进 blocked

**条款提取结果的最小字段**（结构校验按此校验）：

```json
{
  "clauses": [
    {
      "clause_no": "第三条",
      "title": "付款方式",
      "category": "payment",
      "text": "甲方应在验收后90日内支付...",
      "page": 3,
      "char_start": 1280,
      "normalized": { "payment_days": 90, "prepay_ratio": 0.3 },
      "confidence": 0.92
    }
  ],
  "basic_info": { "party_a": "", "party_b": "", "contract_amount": 0, "sign_date": "" }
}
```

- `normalized` 是阈值规则的唯一取值来源，规则引擎不直接解析自然语言。
- `page` + `char_start` 用于定位原文，报告里的“第X页”以此为准。

### 4.3 Skill 3：规则审查（RULE_REVIEW）

- **描述**：两路检索审查合同条款，输出风险点
- **包含的 Tool**：
  - run_pg_rules：跑 PostgreSQL 确定性规则匹配
  - search_manual_semantic：Milvus 语义检索手册参考
  - get_rule_detail：查单条规则详情
- **使用指引**：
  1. 先检查是不是标准版本合同：
     - 标准版 → 只审可修改部分条款
     - 非标准版 → 全量审查
  2. 第一路 PG 规则表：阈值类代码直接比较，关键词类代码正则匹配
  3. 第二路 Milvus 语义检索：遍历 is_semantic 规则，按 semantic_query 批量检索手册参考原文
  4. 把手册参考喂给 AI，判断该条款是否合规
  5. 两路命中结果合并写 rule_hits 表
  6. AI 生成的风险摘要必须基于 rule_hits，不能编造

### 4.4 Skill 4：报告与回写（REPORT_WRITEBACK）

- **描述**：生成审查报告，回写飞书评论区
- **包含的 Tool**：
  - save_result：保存审查结果
  - write_comment：回写飞书评论
- **使用指引**：
  1. 先调 save_result 把审查报告存库
  2. 回写前查 comment_logs，同一 task + attachment_version 已成功回写则跳过
  3. 存库成功后再调 write_comment 回写飞书评论区
  4. 如果是扫描件 OCR，评论开头加一句提示："本合同为扫描件识别，关键金额/日期建议人工核对"
  5. 金额/账期类命中的建议里加一句："（OCR识别数据，建议人工确认）"
  6. 回写失败进 blocked，等人工重试
  7. 回写内容必须包含：风险等级 + 命中规则列表 + 中文摘要 + 审批关注点

## 5. Harness 校验框架（三层 + 重试 + 异常分级）

### 5.1 三层校验器

| 校验器 | 校验什么 | 什么时候触发 |
|---|---|---|
| **结构校验**（复用现有输出模型） | AI输出必须符合固定schema：条款字段全不全、报告格式对不对 | extract_clauses 后、save_result 前 |
| **事实校验**（扩展现有 FactChecker） | AI说的风险点必须有rule_hits记录支撑，不能编造 | AI生成风险摘要后 |
| **动作校验**（新增写操作校验） | 回写评论是写操作，必须记录日志，失败进blocked | write_comment 前 |

### 5.2 重试机制（沿用电商小二 Harness 设计）

校验失败后的处理：

```
校验失败
    |
    v
判断是不是可纠正错误（CorrectableErrorCode）
    |
    +-- 是 → 把错误信息作为 SystemMessage 反馈给 AI → AI 重新生成
    |   → 最多重试 1 次，还失败就 blocked
    |
    +-- 不是（不可纠正）→ 直接 blocked
```

**blocked 任务重试**：记录 `failed_stage`，从失败的那一步继续，不从头跑。
- 预处理 blocked → 重试从下载/解析继续
- 审查 blocked → 重试从规则审查继续
- 如果 blocked 时已经收到过@（review_requested=true），重试成功后自动跑审查

### 5.3 异常分级

| 错误类型 | 处理 |
|---|---|
| 附件缺失/下载失败 | blocked，等人工重试 |
| Word 转 PDF 失败 | blocked，等人工重试 |
| MinerU解析失败/OCR识别不出 | blocked，等人工重试 |
| 解析内容为空 | blocked |
| PG规则匹配失败 | blocked，记录日志 |
| Milvus向量检索失败 | 降级跳过语义类规则，只跑PG确定性规则，记录warn日志 |
| AI输出不符合schema（结构校验失败） | 自动重试1次，还失败就blocked |
| AI编造风险点（事实校验失败） | 自动重试1次，还失败就blocked |
| 模型调用失败/超时/限流 | 自动重试3次，还失败blocked |
| 飞书API回写失败 | blocked，等人工重试 |
| 网络抖动/超时 | 自动重试3次，还失败blocked |

### 5.4 Skill 调用记录

每一次工具调用都记录：
- 调了哪个 Skill
- 调了哪个 Tool
- 入参是什么
- 返回了什么
- 耗时多久
- 成功还是失败
- 失败原因

全部写进 task_logs 表。

## 6. 规则库设计（两路）

### 6.1 规则来源

从《工程造价规范操作手册》PDF 导入，走掌柜智库的导入链路：

| 步骤 | 做什么 |
|---|---|
| 1. PDF→MD | MinerU 解析 PDF 为 Markdown |
| 2. 切片 | 按标题切 section → 长切短合（chunk_size=300, overlap=30） |
| 3. 硬规则 | 人工提炼 20-30 条核心规则 → 存 PostgreSQL |
| 4. 向量库 | 全部切片向量化 → 存 Milvus |

**定时同步**：手册更新后自动同步到 Milvus，标记版本号，区分增量更新（只加新章节）和全量更新（全部重建）。

**规则版本**：PG 规则表改动时 `rule_version` 递增；审查结果记录当时的规则版本。规则改动只影响之后新审的合同，之前审过的不重审。

### 6.2 规则分类

| 分类 | 典型规则 |
|---|---|
| **商务重点** | 预付款比例上限、付款周期上限、保证金比例上限、材料投入率、租金类型 |
| **法务重点** | 印章有效性、违约责任对等性、管辖地、保密条款、知识产权、数据处理 |
| **双方共审** | 背靠背条款、验收标准、自动续约、合同主体完整性 |

### 6.3 PG 规则表结构（硬规则）

```sql
CREATE TABLE review_rules (
    id              SERIAL PRIMARY KEY,
    rule_code       VARCHAR(64) UNIQUE,
    rule_name       VARCHAR(128),
    rule_category   VARCHAR(32),       -- business/legal/both
    risk_level      VARCHAR(16),       -- low/medium/high
    rule_status     VARCHAR(16),       -- enabled/disabled
    match_mode      VARCHAR(32),       -- keyword/regex/threshold/semantic
    match_text      TEXT,
    threshold_value NUMERIC(14,2),
    target_field    VARCHAR(64),       -- 阈值作用字段：payment_days/prepay_ratio/clause_text 等
    operator        VARCHAR(8),        -- > >= < <= = contains regex
    threshold_unit  VARCHAR(16),       -- day/percent/yuan
    is_semantic     BOOLEAN DEFAULT FALSE, -- 是否走 Milvus 语义检索
    semantic_query  TEXT,              -- 语义检索 query 模板
    applies_scope   VARCHAR(32) DEFAULT 'all', -- all/standard_only/nonstandard_only
    rule_version    INT DEFAULT 1,
    suggestion_text TEXT,
    source_page     INT,
    updated_at      TIMESTAMP DEFAULT NOW()
);
```

阈值规则必须同时填 `target_field`、`operator`、`threshold_unit`，否则规则不生效。

### 6.4 Milvus 手册切片库（语义参考）

- 切片方式：按 Markdown 标题切 section → 长切短合（chunk_size=300, overlap=30）
- 存储：71 页手册全部 chunk + 向量（BGE-M3）
- 定时同步：手册更新后自动同步，标记版本号
- 用途：语义类规则判断时，找手册参考原文喂给 AI

### 6.5 两路配合方式

```
合同解析完
    |
    v
第一路：PG 规则表跑确定性匹配（80% 命中）
    |
    v
第二路：遍历 is_semantic 规则（建议 10-15 条）
    -> 每条按 semantic_query 查 Milvus，topK=3
    -> 把手册参考批量喂给 AI 判断（20% 语义类命中）
    |
    v
两路结果合并 → 事实校验 → 生成报告
```

## 9. 飞书审批对接

- **前置验证（阻断项）**：先验证 ① 机器人能否加入审批并出现在评论区；② @ 事件是否携带 approval_code；③ 评论回写接口的格式和长度限制。
- **拉待办**：调飞书开放平台审批API
- **监听@消息**：飞书事件订阅，监听评论区@合同审批助手，根据审批编号匹配 approval_tasks
- **回写评论**：调飞书API往审批评论区写审查意见
- **事件去重**：按 event_id 去重，避免飞书重推导致重复审查。

**降级方案**（前置验证不通过时）：

- 事件订阅不可用 → 轮询评论，按关键词匹配触发。
- 评论区不可用 → 管理后台手动触发，结果写审批表单或单独通知。
- 待确认：飞书审批具体API字段、应用权限申请。

## 11. 验收标准

1. APScheduler 定时拉飞书待办，按 approval_code 去重
2. 自动下载所有附件，Word 转 PDF，多个附件拼接成一个，存 MinIO
3. MinerU 解析 PDF，按掌柜智库方式切片，提取结构化条款，标记是否扫描件
4. 预处理完成后任务状态变 ready
5. 飞书评论区@合同审批助手：
   - 如果已 ready → 立即跑审查
   - 如果还在预处理 → 记 review_requested=true，预处理完自动跑
   - 如果已 done → 直接回复已有结果
6. 两路规则匹配：PG 跑确定性规则 + Milvus 找手册参考
7. 标准版本合同只审可修改部分，非标准版全量审查
8. AI 输出过结构校验和事实校验，不编造
9. 审查结果回写飞书评论区，扫描件加 OCR 提示
10. 校验失败自动重试1次，还失败进 blocked
11. blocked 任务记录 failed_stage，重试从该步骤继续
12. 全链路 Skill/Tool 调用日志可查
13. 同一任务不会重复审查、重复回写评论（条件更新 + comment_logs 去重）
14. 阈值规则能按 target_field / operator / threshold_unit 正确执行
15. 附件更新后按新版本重审，旧结果保留可追溯
